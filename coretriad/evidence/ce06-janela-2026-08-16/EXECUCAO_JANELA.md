## 1. Prova de reversão — 20h53, antes da mudança real


**Reversão provada simétrica e verificável por tamanho de arquivo**, antes de
qualquer alteração de comportamento.

## 2. Aplicação — 20h54m53s

```sql
ALTER SYSTEM SET log_connections    = on;
ALTER SYSTEM SET log_disconnections = on;
ALTER SYSTEM SET log_line_prefix    = '%m [%p] user=%u db=%d host=%h ';
SELECT pg_reload_conf();   -- t
```

`postgresql.auto.conf` após a aplicação:

```
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
log_connections = 'on'
log_disconnections = 'on'
log_line_prefix = '%m [%p] user=%u db=%d host=%h '
```

### Observação técnica registrada

O `SELECT` executado **na mesma sessão**, imediatamente após `pg_reload_conf()`,
ainda devolveu os valores antigos. Não é falha: `pg_reload_conf()` sinaliza os
backends de forma assíncrona, e `log_connections` tem contexto
`superuser-backend` — é fixado na abertura da conexão. **A verificação só é
válida em conexão nova.** Registrado porque um verificador futuro que repita a
checagem na mesma sessão vai concluir, erradamente, que a mudança não pegou.

## 5. Volume real medido — corrige estimativa anterior

Medição de 2 minutos, imediatamente após a ativação:

| Métrica | Valor |
|---|---|
| Linhas | 38,5/min → **~55.400/dia** |
| Bytes | **~8,7 MB/dia** |
| Conexões em 2 min | 20 em `erp_evok_audio`, 1 em `erp_evok_audio_test`, 2 outras |

**Correção de estimativa minha:** o procedimento preparado em
`G4_CE06_LOG_CONNECTIONS.md` §4 dizia que *"com pool persistente do Sequelize, o
regime estável é baixo"*. **Está errado.** O `healthcheck` do container abre e
fecha conexão a cada 10s e o pool do `evok-api` faz o mesmo, o que produz churn
constante — 20 das 23 conexões de 2 minutos são do banco de produção.

Consequência prática: com os 50 MB de rotation do Docker, a margem antes de
perder log é de **~5-6 dias**, não indefinida. A execução diária continua
adequada, mas a folga é menor do que eu havia afirmado. Se o job falhar por uma
semana sem ninguém notar, há perda de evidência — e é exatamente por isso que
ele sai com código de erro em vez de sucesso silencioso.

**Achado lateral, fora do escopo desta janela e não tratado:** o churn de
conexão a cada 10s sugere que o pool do `evok-api` não está sendo reaproveitado
como se supõe. Não investiguei; fica como observação para quem for auditar
performance.
