| Parâmetro | Valor atual | Contexto | Origem | Restart pendente |
|---|---|---|---|---|
| `log_connections` | `off` | `superuser-backend` | `default` | não |
| `log_disconnections` | `off` | `superuser-backend` | `default` | não |
| `log_line_prefix` | `%m [%p]` | `sighup` | `default` | não |

Parâmetros vizinhos relevantes, **que a janela NÃO altera**:

| Parâmetro | Valor | Por que importa |
|---|---|---|
| `logging_collector` | `off` (`postmaster`) | O servidor escreve em **stderr**, capturado pelo driver `json-file` do Docker. É por isso que o job de retenção lê `docker logs` e não um arquivo dentro do container. Mudar exigiria **restart**, e não é necessário |
| `log_destination` | `stderr` | Confirma o caminho acima |
| `log_timezone` | `UTC` (`configuration file`) | Único parâmetro `log*` que **não** está em `default` — vem do arquivo de configuração, não de `ALTER SYSTEM` |
| `log_statement` | `none` | **Permanece `none`.** A janela registra *conexões*, não *comandos*. Volume e sensibilidade de `log_statement=all` são outra ordem de grandeza e não estão aprovados |

Os outros 32 parâmetros `log*` estão todos em `source = default` e não são tocados.

## 3. Runbook da janela — a executar às 22h00

### 3.0 — Prova da reversão, ANTES da mudança real

Primeiro ato da janela, deliberadamente **sem efeito comportamental**: fixar
`log_connections` no valor que ele já tem (`off`), recarregar, conferir, e
reverter. Prova o mecanismo `ALTER SYSTEM` + `RESET` + `pg_reload_conf()` sobre
**o parâmetro exato** que será alterado, sem mudar comportamento nenhum.

```sql
ALTER SYSTEM SET log_connections = off;   -- off -> off: no-op semântico
SELECT pg_reload_conf();
-- conferir: postgresql.auto.conf passou a ter a linha
ALTER SYSTEM RESET log_connections;
SELECT pg_reload_conf();
-- conferir: postgresql.auto.conf voltou a 88 bytes
```

Não foi executado antes da janela de propósito: é escrita no cluster de
produção, e a instrução do dono é que escrita só ocorre dentro da janela.

### 3.1 — A mudança

```sql
ALTER SYSTEM SET log_connections    = on;
ALTER SYSTEM SET log_disconnections = on;
ALTER SYSTEM SET log_line_prefix    = '%m [%p] user=%u db=%d host=%h ';
SELECT pg_reload_conf();
```

**`log_line_prefix` é obrigatório, não enfeite.** O default `%m [%p]` traz só
timestamp e PID: o log registraria que houve conexão sem permitir **atribuí-la**
— exatamente o que o `CE-06` exige. Sem usuário, banco e host, a evidência não
serve para o fim que motivou o critério.

**Reload, não restart.** Os três são aplicáveis por `SIGHUP`; `log_connections`
e `log_disconnections` passam a valer para **conexões novas**. O pool já aberto
do `evok-api` não é afetado retroativamente. **Sem downtime.**

### 3.2 — Verificação pós-aplicação

1. `pg_settings` dos três parâmetros: valor esperado e `source = configuration file`.
2. `pg_isready` e uma consulta trivial: o banco responde normalmente.
3. Abrir uma conexão nova e confirmar a linha `connection authorized` no log,
   **com `user=`, `db=` e `host=` preenchidos**.
4. Repetir para **os dois bancos**, provando que o escopo de cluster funciona
   como previsto — esta é a metade que faltava da prova da retenção (`R-21`).
5. Rodar o job de retenção e confirmar que a linha real foi capturada no
   arquivo append-only.

### 3.3 — Reversão, se algo sair errado

```sql
ALTER SYSTEM RESET log_connections;
ALTER SYSTEM RESET log_disconnections;
ALTER SYSTEM RESET log_line_prefix;
SELECT pg_reload_conf();
```

Critério de conferência: `postgresql.auto.conf` de volta a **88 bytes** e os três
parâmetros de volta a `source = default`. Simétrica, imediata, sem downtime.

## 4. O que este documento NÃO faz

- **Nada foi alterado no cluster.** Todas as saídas acima são leitura.
- Não declara `CE-06` satisfeito. Ligar o parâmetro é metade; a outra metade é

- Não altera `logging_collector`, `log_statement` nem qualquer outro parâmetro
  além dos três nomeados.
- Não autoriza nada por si: a autorização é `APR-2026-028` §2 mais a confirmação
  de dia e horário dada pelo dono.
