# REMEDIAÇÃO CASE-007: AUD-AUTHN-03 — Rate Limit com JWT.verify (não decode)

Você é sanacore-remediation-engineer executando a remediação CASE-007.
Tarefa: trocar `jwt.decode()` por `jwt.verify()` no apiRequestKey rate limiter.

## Problema (Causa-Raiz Confirmada)

`app.ts:79` usa `jwt.decode()` que lê payload JSON SEM verificar assinatura.
Consequência: qualquer pessoa pode forjar um JWT com payload `{id: "user123"}` e particionar por esse usuário,
contornando o rate limit global que deveria conter abuso por conta.

Cenário de ataque:
- Atacante cria 100 JWTs com IDs diferentes (sem assinatura válida)
- Cada um usa uma chave `user:ID_forjado` diferente
- Rate limiter acha que são 100 usuários legítimos → limite não ativa
- DoS dirigido a um usuário legítimo fica invisível

## Escopo (EXATO — não estenda)

E-1. `server/app.ts:79` → TROCAR `jwt.decode(token)` por `jwt.verify(token, process.env.JWT_SECRET)`
E-2. `server/app.ts:84-86` → Envolver em try/catch:
     - Se verify falha → fallback para `ipKeyGenerator(req.ip)` (comportamento seguro)
     - Se JWT inválido → usa chave por IP (compartilhado, desacelera ataque também)
E-3. `server/tests/setup.ts:5` → ADICIONAR `process.env.DB_NAME = 'erp_evok_audio_test'`
     - Razão: NODE_ENV=test não define DB_NAME, cai no default de runtimeEnv (banco de produção)
     - Consequência: suite tenta conectar ao banco real ❌
E-4. **Criar teste novo:** `server/tests/integration/rate-limit-jwt-verify.test.ts`
     → Caso 1: 301 requisições em 15 min com JWT VÁLIDO → 429 (atingiu limite por usuário)
     → Caso 2: 301 requisições em 15 min com JWT INVÁLIDO → fallback para IP, cada uma conta no pool de IP
     → Caso 3: 301 requisições de IPs diferentes com JWT VÁLIDO → cada IP tem sua cota (não compartilha)
E-5. VALIDAR: `npm run test:integration` roda sem conectar banco de produção

## Critérios de Sucesso (DEVE passar todos)

- [ ] Suite de integração roda sem conectar banco de produção (NODE_ENV=test + DB_NAME=test)
- [ ] `npm run test:unit` → 431/431 testes passam
- [ ] `npm run test:integration` → 27 suites, 65 testes, 100% passam
- [ ] Rate limit respeita cota POR USUÁRIO autenticado (300 req/15min)
- [ ] Token inválido → fallback para IP (sem erro 500, sem derrubar servidor)
- [ ] Teste novo cobrindo os 3 cenários acima
- [ ] Nenhuma alteração em docker-compose.yml, Dockerfile, ou compose.prod.yml

## Desvios Conhecidos (NÃO ESTENDA)

- ⚠️ TRUST_PROXY continua 0 (não é escopo de CASE-007)
- ⚠️ D1=1600 req/min por IP já aprovado (APR-2026-052) — não altere
- ⚠️ D2=300/15min por usuário já aprovado — não altere
- ❌ Não tocar em `compose.yml` ou criar variável nova de configuração
- ❌ Não mudar lógica de `refreshLimiter` (outro limiter, outro caso)
- ⚠️ Se encontrar outro lugar usando `jwt.decode()` sem verify, registre mas não estenda escopo aqui

## Tecnologia

- Auth: jsonwebtoken (npm package)
- Framework: Express
- Rate Limit: express-rate-limit
- Teste: Jest + Supertest (integração)

## Armadilhas Conhecidas

1. **NODE_ENV=test sem DB_NAME** → suite tenta conectar ao banco de produção
   → Solução: E-3 adiciona `process.env.DB_NAME = 'erp_evok_audio_test'` em setup.ts
   
2. **jwt.verify com secret errado** → Exception diferente de verify falha
   → Solução: try/catch captura qualquer exception, fallback para IP
   
3. **Token expirado** → jwt.verify lança erro (correto), fallback ativa
   → Esperado e seguro
